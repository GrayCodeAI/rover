# Repair Rover truth before expanding scope

> This report records the pre-change audit baseline. A first release-truth slice was implemented after the audit; the original findings remain as the baseline for measuring that work.

## Implementation checkpoint after the audit

- `VERSION` now drives Makefile linker metadata, and the CLI reports the injected commit.
- `make version-check` validates the runtime, SDK, capability, README, roadmap, status, changelog, manifest, and release-workflow version surfaces.
- `make manifest` and `make manifest-check` now generate and verify a complete tracked-source inventory; the generator excludes the manifest itself and research artifacts.
- CI and the manual release workflow run the version and manifest checks, validate the release tag, verify the built source package, use explicit target flags, and remove unused OIDC permission.
- `make cross-build` now fails rather than mislabeling a host binary when the Linux cgo toolchain is unavailable; the Darwin cgo-free legs were compiled locally, while the Linux leg still requires an owned Linux/cgo environment.
- Candidate-controlled JUnit and regression XML now share size, token, depth, and DTD/entity bounds; `make fuzz` now runs all five repository fuzzers.
- Go 1.26.6 is now the enforced minimum in `go.mod`, Make, CI, release, and regression checks; `govulncheck` is pinned to v1.8.0 and the local scan is green.

The vulnerability gate is now green on Go 1.26.6. Release/artifact hardening is not complete until the Linux leg, release smoke, and independent review are run.

Rover is a **terminal-first, agent-neutral local supervisory and assurance layer**, not another model-agent loop and not a claim of hostile-code isolation, protected CI acceptance, universal provider support, or production multi-host operation. Its strongest engineering property is a shared core that keeps execution, candidate identity, structured interpretation, policy decision, review, and evidence distinct across CLI/JSON, TUI, SDK, MCP, tasks, and workflows. The current Darwin checkout passes ordinary tests, race tests, both fixture demos, SDK tests, and the three fuzz targets wired into `make fuzz`, but the public truth and release surfaces are not release-ready: version identities conflict, the source manifest is stale, acceptance statuses are overstated, the release workflow can attach the wrong or nonfunctional artifacts, and the current vulnerability gate fails. Across a relevance-weighted set of 20 OSS projects, the strongest common pattern is **candidate identity → fixed acceptance contract → isolated observation → typed outcome → retained provenance → separately authorized decision**, not “agent plus benchmark plus security score.” The single most important next move is therefore to establish an **evidence-bound release truth gate**: one canonical version, a complete commit-bound validation record, an externally anchored source/release manifest, functional artifacts, honest acceptance taxonomy, and a green supported-toolchain vulnerability scan. Until that gate exists, Rover should freeze feature breadth and spend the next releases on truth repair, integrity/lifecycle hardening, parser/evaluation depth, real isolation, and independent review—not RL, marketplaces, broad clients, or automatic publication.

## Decision: preserve the control plane, repair its truth

### What Rover is—and is not

Rover’s defensible product identity is narrow and valuable. **Observed:** the architecture routes public interfaces into the same task, snapshot, assurance, and storage implementations rather than giving each client a separate acceptance engine (`docs/ARCHITECTURE.md:3-24`, `internal/cli/cli.go:199-300`, `internal/service/service.go:40-54`). **Observed:** explicit argv, retained source bytes, candidate/spec digests, incomplete-evidence refusal, and a separate local review record are implemented rather than merely described (`internal/execution/process.go:158-270`, `internal/source/source.go:178-344`, `internal/assurance/verify.go:51-107`, `internal/assurance/verify.go:254-266`). **Documented intent:** Rover’s intended destination is full-platform, but the present product is an alpha and local execution is explicitly not a sandbox (`README.md:165-182`, `docs/SECURITY_MODEL.md:3-13`).

| Rover is | Rover is not |
|---|---|
| A terminal-first supervisor and evidence/assurance substrate around existing agents | A model-inference loop or a replacement for coding agents |
| An exact-snapshot and typed-result system for local candidates | A universal correctness, security, or formal-proof oracle |
| A bounded local task/DAG runtime with worktrees, PTYs, repair, review, and replay | A hostile-code sandbox, VM service, or tenant isolation boundary |
| An agent-neutral application core with CLI, JSON, TUI, thin SDKs, and bounded MCP interfaces | A certified Codex, Claude, ACP, MCP, A2A, or provider-conformance implementation |
| A local evidence store with explicit-key signatures, backup, and bounded export | SLSA/in-toto provenance, independent acceptance, transparency logging, or a protected publisher |
| An offline check-order experiment with explicit local promotion | RL, autonomous self-improvement, self-modifying policy, or a defect oracle |
| A foundation that can later call reviewed verifier/compute adapters | A cloud execution fleet, plugin economy, hosted multi-tenant service, or automatic merge/deploy system |

The right strategic decision is to **preserve the control-plane position**. The 20-project comparison shows that broad agent clients repeatedly accumulate chat, connectors, marketplaces, cloud synchronization, and provider-specific state ([Gemini CLI](https://github.com/google-gemini/gemini-cli), [Cline](https://github.com/cline/cline), [Goose](https://github.com/aaif-goose/goose), [OpenCode](https://github.com/anomalyco/opencode)). Copying that feature surface would blur Rover’s differentiator and multiply authority, privacy, replay, and lifecycle risks. Rover should instead import portable contracts—capability negotiation, event lineage, explicit execution profiles, independent review, idempotent effects, and candidate-bound evidence—while keeping the terminal path complete and making every remote or optional path an adapter outside the acceptance core.

### The single next move: establish the release truth gate

The first coherent milestone should be a mechanically enforced **Release Truth Gate**, not another capability. It should make it impossible to describe or attach a release unless all of the following refer to the same immutable commit:

1. One canonical version injected into the binary, `VERSION`, SDK metadata, release tag input, manifest, and generated public documentation.
2. A complete source and artifact manifest bound to that commit, tool versions, target OS/architecture, and externally supplied expected digest or signature—not merely a hash list next to files it describes.
3. Fresh validation evidence for `make check`, `make race`, SDK tests, all fuzz targets, all schema examples, both demos, functional artifact smoke, and the vulnerability gate.
4. A four-state acceptance matrix that distinguishes original-scenario implementation, partial behavior, adjacent proxy/safe absence, and unimplemented behavior.
5. Release artifacts that are architecture-correct, version-correct, and functionally open a real store; unsupported probes must not be published as normal Rover binaries.
6. User-facing command/API documentation generated or smoke-tested against the actual parser and enums.

This gate addresses the highest-risk observed contradictions directly: runtime version `0.0.1` versus public status surfaces at `0.2.0-alpha.1` (`internal/model/model.go:15-16`, `VERSION:1`, `ROADMAP.md:6-11`, `docs/capabilities.json:2-4`); a current `doctor --verify` size mismatch against `SOURCE_MANIFEST.json` (`SOURCE_MANIFEST.json:2-24`); three incompatible acceptance views (`docs/acceptance/README.md:1-47`, `docs/PLAN_ALL.md:69-72`, `STATUS.md:232-238`); and a release workflow that references a missing Linux artifact while attaching cgo-disabled Darwin store stubs (`.github/workflows/release.yml:35-66`, `internal/store/sqlite_stub.go:144-176`). Until those are repaired, adding adapters or clients would make the product easier to use but less trustworthy about what it has actually proven.

They were reconciled by **canonical repository identity**, not brand name or old redirect. The resulting shortlist is relevance-weighted for Rover rather than sorted as a universal “top 20”: **30% direct control-plane relevance**, **25% complementary isolation/orchestration/provenance value**, **15% current maintenance and ecosystem significance**, **15% useful interface/extensibility patterns**, **10% evidence depth in the notes**, and **5% fit with terminal-first, privacy-preserving operation**. ### End-to-end flows

**1. Ingress and shared application core.** **Observed:** `main` creates a signal-aware context and calls `cli.New(...).Main` (`cmd/rover/main.go:12-16`). `App.run` parses only global `--state`, resolves `$ROVER_HOME`/OS config defaults, then dispatches basic and extended commands (`internal/cli/cli.go:134-208`). The TUI reads the same task/investigation records rather than maintaining an independent authority (`internal/cli/terminalui.go:71-183`). The SDKs invoke the CLI without a shell, and remote control uses the bounded MCP client rather than a second task engine (`sdk/go/rover_client.go:71-103`, `internal/mcp/client.go:74-167`). **Inference:** terminal-first is more than branding here; it is the canonical control path, with other clients expected to call the same use cases.

**2. Configuration, state, and source identity.** **Observed:** state admission canonicalizes allowed OS temp ancestors, rejects unsafe final/intermediate links, refuses unrelated populated directories, creates private subdirectories, and initializes SQLite schema version 1 (`internal/store/sqlite.go:61-258`). The approved config normally comes from the immutable base snapshot; a candidate config change is a finding, not a replacement policy (`internal/assurance/verify.go:28-50`, `internal/source/source.go:461-499`). Committed capture uses Git objects; worktree capture performs two content reads and labels the result non-atomic (`internal/source/source.go:178-344`). Files are retained as content-addressed objects and materialized with no-follow/exclusive creation (`internal/store/sqlite.go:467-535`, `internal/source/source.go:356-398`). **Inference:** the source identity model is the strongest part of Rover and should become the anchor for every future adapter and evidence format.

**3. Task, supervisor, and PTY flow.** **Observed:** submission validates explicit local authority, resolves the base to a commit, captures a base snapshot, freezes the approved config, creates an idempotent task record, and starts either foreground execution or a hidden detached supervisor (`internal/tasks/tasks.go:47-129`). The supervisor creates a worktree, optionally replaces it with an exact input snapshot, waits for named resource leases, runs each attempt, retains stdout/stderr, parses native provider claims, captures a candidate, and verifies it with the original frozen config (`internal/tasks/tasks.go:195-455`). PTY tasks use a one-writer Unix socket, bounded ring/replay, resize, input, and detach (`internal/execution/pty_linux.go:74-228`, `internal/execution/attach.go:17-116`). **Inference:** this is a credible local agent supervisor, but the trust unit remains the same OS user; “detached” is lifecycle convenience, not isolation or cross-host recovery.

**4. Workflow and integration flow.** **Observed:** workflow validation rejects cycles, unknown/duplicate edges, node policy replacement, and non-auto-verified nodes (`internal/workflow/workflow.go:70-142`). Each ready node receives a composed parent snapshot; unreviewed handoffs require an explicit policy exception; leaf candidates are merged conservatively and the actual integrated snapshot is verified again (`internal/workflow/workflow.go:382-570`). **Inference:** this is a useful bounded DAG, not Temporal-style durable replay and not an external merge queue.

**5. Verification and assurance flow.** **Observed:** each check gets a fresh materialized candidate, preexisting report files are refused, execution output and structured report are retained, inputs are rechecked, and only then is the result interpreted (`internal/assurance/verify.go:167-246`). A required check must match the candidate and spec digest and return `PASS`; missing/error stays inconclusive, failure blocks, and review policy produces `REVIEW_REQUIRED` (`internal/assurance/verify.go:51-107`). Counterfactual proof requires the same uniquely identified test to fail for the expected reason on base and pass on candidate (`internal/assurance/counterfactual.go:37-110`). **Inference:** Rover already has the correct evidence-failure discipline; the next work is stronger parser/adversarial coverage and independent authority, not a green-total redesign.

**6. Grants, MCP, HTTP, and remote control.** **Observed:** tokens are stored by digest and scoped to project, audience, tool, expiry, and revocation (`internal/access/grants.go:46-120`). The service excludes grant, review, signing, policy, merge, and deployment tools and revalidates network grants at call time (`internal/service/service.go:64-153`). HTTP rejects browser origins, requires JSON and a bearer grant, bounds messages/concurrency, supports cancellation, and requires TLS for non-loopback listeners (`internal/mcp/http.go:19-201`). The remote client refuses plaintext non-loopback endpoints, proxies, redirects, and credential query strings (`internal/mcp/client.go:34-127`). **Inference:** this is a strong API boundary for a local controller, but not an OS tenant boundary and not remote worker fencing.

**7. Context, instructions, and learning.** **Observed:** context is literal, snapshot-bound, size/line bounded, excludes selected sensitive filenames, and best-effort redacts inline patterns (`internal/contextstore/context.go:35-114`). Instruction integration previews a managed block, stores prior bytes, applies, and refuses stale undo (`internal/integration/instructions.go:82-220`). Learning proposes a complete permutation, binds config/candidate/spec evidence, evaluates a disjoint holdout, requires explicit local promotion, and applies only through explicit `verify --strategy` (`internal/learning/learning.go:87-185`, `internal/learning/learning.go:262-395`). **Inference:** this is a disciplined local experiment, not learning-based authority. Its strongest future role is producing auditable recommendations for humans, never changing required checks.

**8. Evidence, backup, signature, and publication.** **Observed:** backup takes an online SQLite copy plus retained objects and writes hashes only after copy completion; restore requires a new tree, verifies hashes, revokes grants, releases leases, and marks active work lost (`internal/archive/archive.go:142-256`, `internal/archive/archive.go:258-358`). Signing covers a domain-separated payload containing the finished investigation and referenced config/output/report artifacts under an explicitly selected key (`internal/attestation/sign.go:109-164`). `publish` writes one local JSON copy with exclusive creation (`internal/publish/publish.go:14-58`). **Inference:** the evidence model is appropriately modest. The next upgrade is tamper-evident lineage and protected custody—not broader signature language.

**9. Build, CI, and release.** **Observed:** `make check` is format/vet/test; `make race` is the full race suite; demos build and run owned fixtures; SDK tests are wrappers; fuzz wires three campaigns; cross-build produces Linux and two cgo-disabled Darwin files (`Makefile:7-73`). CI config includes the same checks and release config is manual (` .github/workflows/ci.yml:23-44`, `.github/workflows/release.yml:32-66`). **Observed:** the cgo-disabled store returns `errNoCGO` for state operations (`internal/store/sqlite_stub.go:144-176`). **Inference:** compilation is not platform support, and a manually triggered workflow is not automatically safe publication.

### Concrete strengths worth preserving

1. **Candidate and policy binding.** Snapshot IDs derive from repository identity and file manifests; check results bind candidate and spec digest; config comes from base; replay creates a new investigation rather than rewriting history (`internal/source/source.go:172-177`, `internal/assurance/verify.go:76-86`, `internal/assurance/counterfactual.go:196-224`).
2. **Fail-closed evidence interpretation.** Timeout, cancellation, truncation, malformed reports, missing required checks, no tests, and no required plan do not silently become acceptance (`internal/assurance/parse.go:22-68`, `internal/assurance/parse.go:134-160`, `internal/assurance/verify.go:51-107`).
3. **Agent-neutral domain core.** Native adapters emit process/session/usage claims but do not define verification decisions (`internal/agents/agents.go:1-3`, `internal/agents/agents.go:143-258`).
4. **Authority-tool separation.** MCP/API cannot mint grants, approve reviews, sign, merge, deploy, or change policy (`internal/service/service.go:64-92`, `docs/SECURITY_MODEL.md:15-30`).
5. **Conservative composition.** Contradictory leaf edits stop instead of being guessed; integrated bytes are reverified (`internal/source/compose.go:118-155`, `internal/workflow/workflow.go:529-569`).
6. **Reversible/local-first operations.** Guidance is previewable and undoable; backup/restore sanitizes execution; cancellation never claims to reverse external effects (`internal/integration/instructions.go:151-220`, `internal/archive/archive.go:315-356`, `internal/cli/cli.go:234-247`).
7. **Useful negative-path tests.** Malformed JSON/transcripts, static symlink/path states, report incompleteness, grant expiry/revocation, duplicate in-flight requests, backup tampering, key mismatch, learning overlap, and no-fallback admission are covered (`internal/config/config_test.go:15-162`, `internal/agents/agents_test.go:55-118`, `internal/service/service_test.go:20-334`, `internal/archive/archive_test.go:18-152`).

### The composite architecture Rover should keep

The comparison supports a layered architecture in which each project contributes one narrow, composable property:

1. **Identity and contract:** Rover already has the strongest base. Candidate, base, config/policy, check spec, environment, and parser/tool versions must be bound before execution. External benchmark or evidence formats import into this canonical envelope; they do not replace it.
2. **Execution profile:** local read-only, local workspace-write, restricted container, remote environment, and OS-sandboxed workspace-write must be separate negotiated classes. Approval is a policy operation; isolation is a technical property; neither implies the other.
3. **Observation:** retain raw output and structured reports separately. Parse into `PASS`, `FAIL`, `ERROR`, `INCONCLUSIVE`, and `NOT_APPLICABLE`; preserve coverage, tool version, policy, environment, and assumptions.
4. **Event lineage:** keep append-only requests, tool calls, results, file changes, policy decisions, checkpoints, verification, review, and external-effect intent. Summaries and compacted context are derived artifacts with source ranges and supersession links.
5. **Authority and effects:** producer, evaluator, policy administrator, reviewer, signer, and external publisher are separate roles. A model may propose or rank; it may not silently promote, approve, sign, merge, deploy, or create authority.
6. **Recovery and idempotency:** every side effect has a stable operation ID, durable intent, attempt identity, and `UNKNOWN_OUTCOME` reconciliation. Retry is never assumed safe merely because the workflow state is durable.
7. **Privacy by destination:** local evidence, local diagnostic trace, optional OTLP, provider processing, collaborative sharing, registry transparency, and cloud execution each have an independent setting, destination, payload class, retention, and revocation policy.

This composite preserves Rover’s terminal-first, agent-neutral, full-platform destination while avoiding automatic external writes, secret upload, and provider-shaped trust assumptions.

### Verification plan and limitations

#### Required release gate after implementation

The following should become one immutable, commit-bound release procedure. Current targets are shown exactly; proposed targets are marked as additions rather than existing commands.

```sh
make version-check          # proposed: canonical build/release identity
make check                  # current: fmt-check, go vet, full Go tests
make race                   # current: full race-enabled Go tests
make fuzz-all               # proposed: all current and added fuzz targets
make schema-check           # proposed: every schema/example pair
make demo                   # current: 12 owned-fixture scenarios
make demo-extended          # current: 16 owned-fixture scenarios
make sdk-test               # current: Python, TypeScript, Go SDKs
make cross-build            # current: must become explicit and functional per target
make sbom                   # current: must emit standard SPDX or CycloneDX
make vulncheck              # current: must use a pinned scanner and patched toolchain
./bin/rover doctor --verify --json
make release-smoke          # proposed: version/store/artifact support matrix
```

On an owned Linux/amd64 runner with a supported Go release, system SQLite/cgo, Git, Python, a C compiler, and the declared runtime matrix, the same commands must run on the immutable candidate commit. Hosted CI must execute rather than merely exist in YAML. A separate independent host should run hostile-worker, TLS, remote-fencing, and provider-compatibility tests; a local daemon smoke is not independent review. A protected reviewer/evaluator must be able to reject a candidate-controlled policy or result.

#### Current limitations that remain decision-relevant

- **Historical is not current:** the v0.2.0 validation report records Go 1.23.2/Linux/amd64 and prior demo/fuzz results, but current HEAD is Go 1.26.5/Darwin/arm64 and the current manifest and vulnerability gate fail (`docs/validation/v0.2.0/REPORT.md:72-111`).
- **No hosted CI proof:** `.github/workflows/ci.yml` is configuration only; no passing public run may be inferred (` .github/workflows/ci.yml:1-46`).
- **No release dry run:** the manual release workflow was not executed; static defects and current ignored artifact inspection are sufficient to block use, but not a claim about GitHub release behavior.
- **No independent security review:** TOCTOU, same-user state mutation, XML hardening, release permissions, and migration design remain code-review findings until independently tested/reviewed.
- **No live provider matrix:** native profiles have owned JSONL and subprocess fixtures only; account permissions, CLI versions, cancellation, and transcript compatibility remain unverified.
- **No independent host/fleet:** remote CLI and local HTTP/TLS tests do not establish WAN behavior, worker recovery, host loss, or fencing.
- **No hostile-code certification:** restricted Docker flags and a recorded local smoke do not establish credential, kernel, container-runtime, or tenant isolation.
- **No complete schema/retention/erasure proof:** current schemas are useful contracts, but example validation, global quota/GC, complete export/import, and deletion semantics are unfinished.
- **No security or compliance certification:** local Ed25519 proves signature validity under a supplied key; it is not SLSA, in-toto correctness, independent review, or protected acceptance.

## Conclusion

The comparison changes the likely roadmap from “fill the ten layers with more features” to **make one narrow control plane irreducibly trustworthy**. The external projects reinforce Rover’s existing direction: agent runs may generate transcripts and context, compute backends may execute, workflow engines may recover state, scanners and benchmarks may produce evidence, and signing systems may authenticate artifacts, but none may collapse those roles into a single provider, score, signature, or local administrator. Rover’s durable advantage is the exact boundary between those claims.

The next successful release should therefore be smaller and less dramatic than the original ten-layer vision but more credible: one version, one current validation bundle, one explicit acceptance taxonomy, functional artifacts, green supported-toolchain scanning, digest-bound policy, and independently reviewable evidence. Once that exists, Rover can add execution backends, protocols, and platforms as narrow adapters without allowing any of them to redefine acceptance or external authority.
