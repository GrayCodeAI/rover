# Rover roadmap and traceability audit

## Claimed-feature traceability

### Takeaway

Rover is a substantial and internally coherent **local advisory alpha**, not a completed ten-layer platform. Its strongest implemented path is terminal-first and agent-neutral: CLI/JSON, explicit argv, frozen snapshots, bounded checks, SQLite evidence, review, and fixture-driven workflows share the same core semantics. The design reference correctly requires the broader terminal-first, agent-neutral, full-platform destination and separates working code from evidence. [Design scope](../../docs/design/Rover_Ten_Layer_Master_Plan.md#L7-L13) [Architecture](../../docs/ARCHITECTURE.md#L1-L5) [Security model](../../docs/SECURITY_MODEL.md#L3-L13)

This audit observed `make check`, `make race`, and `make sdk-test` pass on 2026-09-24 against HEAD `4e02236` with no pre-existing working-tree changes, using Go 1.26.5 on Darwin/arm64 with cgo enabled. Those commands validate the current tree, but not the recorded Linux/amd64 release envelope, demos, Docker behavior, hosted CI, or live providers. The target definitions are in the [Makefile](../../Makefile#L7-L29) and [Makefile](../../Makefile#L67-L73).

The highest-risk discrepancies are not missing aspirational features; they are **truth-surface conflicts**: four version identities, three incompatible acceptance-status views, stale historical validation manifests, a release workflow that packages non-functional Darwin stub binaries, incomplete default fuzz coverage, and user documentation that disagrees with actual commands and enums. Status terms in this matrix are deliberately narrower than the repository's `tested_local` label:

- **Implemented locally** — the claimed behavior exists and has a relevant test in the current source.
- **Partial** — useful local behavior exists, but the stated boundary is materially narrower.
- **Proxy/absence** — an adjacent check or safe nonexistence exists, but it does not satisfy the broader claim.
- **Recorded only** — documentation reports an observation, but this audit did not reproduce it and/or the evidence is not bound to the current tree.

### Inferences

- The current architecture preserves terminal-first behavior because all SDK, MCP, and remote paths call the same local task/snapshot/assurance records rather than a provider-specific acceptance engine. [ARCHITECTURE.md](../../docs/ARCHITECTURE.md#L1-L24)
- Agent neutrality is real only at the generic-core level. Native Codex/Claude behavior is fixture-shaped and explicitly uncertified; the core should continue to avoid provider-specific verdicts. [agents.go](../../internal/agents/agents.go#L1-L3) [README](../../README.md#L70-L75)
- Full-platform scope should remain a destination. The immediate honest target is a declared support matrix with functional artifacts, not equal Windows/macOS/Linux behavior inferred from compilation.
- The local trust boundary is consistently disclosed in implementation and security documentation. The main risk is not concealment of that boundary; it is aggregate status language that turns scoped local proxies into “40 tested” headlines. [STATUS.md](../../STATUS.md#L232-L238) [implementation-map interpretation](../../docs/acceptance/implementation-map.json#L1-L4)

## Acceptance-scenario traceability

### Takeaway

The repository’s original 40-case inventory remains the correct acceptance source. [Acceptance inventory](../../docs/acceptance/Rover_Acceptance_Test_Specs.json#L1-L396) The current JSON map is useful as a **test-reference index**, but its `tested_local` status does not mean the original acceptance condition was met. [implementation-map.json](../../docs/acceptance/implementation-map.json#L1-L382)

On the original scenarios, this audit classifies **15 as implemented locally, 18 as partial, and 7 as proxy/absence-only**. This is an evidence-qualified assessment, not a test-suite result. The largest overstatement risk comes from A02, A08, A17, A28, A31, A33, and A39 being counted as tested even though the original signed installer, task-budget, prompt-injection, external reconciliation, protected CI, interrupted upgrade, or destructive-delivery behavior does not exist.

Documentation contains three conflicting views: the historical acceptance README says many cases are deferred/partial; `PLAN_ALL.md` says eleven remain partial; the implementation map and STATUS say all 40 are tested with zero partial. ### Inferences

- `tested_local` is acceptable only if renamed or accompanied by a machine-readable `original_acceptance_status`. At present it conflates an actual scenario test with a nearby invariant, safe absence, or a different component’s test.
- The 15 locally implemented cases demonstrate a coherent local verification core, especially snapshots, workflow dependency integrity, parser completeness, counterfactuals, and no-op semantics. They do not justify the broader L1–L10 production claims.
- A26 and A38 are examples of implementing the safety outcome by refusal/no reuse rather than shipping the aspirational subsystem. That is legitimate and should be labeled precisely.
- A39’s absence is safety-positive but should be reported as “no destructive delivery implemented,” not as a tested destructive-delivery workflow.
- The original use cases U01–U16 remain a destination inventory. Several map to partial local proxies, while remote, team, semantic, formal, recurring, and multi-repository use cases remain largely unimplemented. [Master plan use cases](../../docs/design/Rover_Ten_Layer_Master_Plan.md#L372-L407)

## Prioritized backlog and contradictions

### Takeaway

The next work should first make Rover’s **release and evidence truth coherent**, then deepen security and platform contracts. Do not begin with RL, desktop/mobile, a plugin marketplace, or more adapters. Those later enhancements are valuable only after the terminal-first core has one canonical version, an honest acceptance taxonomy, reproducible current-tree evidence, and trustworthy release artifacts.

### Inferences

- The correct sequencing is **truth repair → protected vertical slice → real workflows → broader platform**. Adding providers, formal tools, remote workers, or clients before fixing the evidence contract multiplies contradictory claims.
- Terminal-first should remain the default interface and operational fallback. MCP, SDKs, HTTP, desktop, and mobile should call the same use cases; none should gain a stronger acceptance authority.
- Agent neutrality should be enforced by keeping TaskContract, snapshot, check, evidence, and decision schemas provider-neutral. Native profiles supply execution/claims only.
- Full-platform scope should be retained as a destination, with explicit per-OS/per-runtime capability records. Compilation of a stub is not platform support.
- Evidence honesty is a product feature: current limitations, skipped tests, stale artifacts, and failed external prerequisites must remain visible in status, reports, and release gates.

### Gaps

- Priority ordering is based on local repository evidence only; no external competitor, hosted provider, package registry, organization, or production environment was available or assumed.
- No claim here should be read as live-provider, hosted-CI, protected-publisher, independent-worker, or security-certification evidence.
- The report intentionally did not run `make build`, `make demo`, `make demo-extended`, `make install`, `make cross-build`, Docker, network server, or fuzz commands because those steps can write build/fuzz artifacts and the assignment required no file modifications. Fresh current-tree evidence is limited to `make check`, `make race`, and `make sdk-test`; historical demo evidence is cited as historical only.
- Before implementing backlog items, maintainers should select explicit domain owners, versioned contracts, regression tests, and evidence gates as required by the repository’s contribution policy. [CONTRIBUTING.md](../../CONTRIBUTING.md#L6-L25)
