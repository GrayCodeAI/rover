#### Project-specific identity and governance notes

- **SWE-bench:** the benchmark's unit of evaluation is a historical GitHub issue, its repository state, a reference change containing tests, and a model-produced patch. The official documentation and ICLR 2024 paper identify this benchmark purpose. ([official overview](https://www.swebench.com/SWE-bench/), [paper](https://arxiv.org/abs/2310.06770))
- **Agentless:** the repository and paper identify a deliberately non-agentic software-repair approach in which an LLM performs bounded subtasks but does not autonomously choose an open-ended tool/action loop. ([README](https://github.com/OpenAutoCoder/Agentless#-about), [paper, 2024](https://arxiv.org/abs/2407.01489))
- **Inspect AI:** the framework is not itself a benchmark leaderboard or patch acceptor. Its core abstraction combines a dataset, solver/agent, and scorer, and it can execute both deterministic and model-graded evaluations. ([official site](https://inspect.aisi.org.uk/), [scoring policy](https://inspect.aisi.org.uk/scoring-policy.html))
- **Semgrep:** repository popularity and LGPL coverage must not be represented as coverage of the whole Semgrep product. The maintainers explicitly distinguish Community Edition from the proprietary AppSec Platform, Code, Secrets, Supply Chain, and Pro Engine. ([licensing](https://semgrep.dev/docs/licensing), [repository README](https://github.com/semgrep/semgrep#semgrep-ecosystem))
- **OpenSSF Scorecard:** its purpose is project-governance and supply-chain-practice assessment, not source-level correctness proof or a complete software vulnerability finding set. The maintainers call its checks heuristics with false positives and false negatives and explicitly reject a one-size-fits-all aggregate. ([README, “Project Non-Goals”](https://github.com/ossf/scorecard#project-non-goals))

### Inferences

- Stars indicate adoption interest, not assurance quality. A benchmark score, a static-analysis finding, a repository-posture score, and an evaluation-log verdict have different meanings and should never be collapsed into one unqualified “pass.” ([SWE-bench overview](https://www.swebench.com/SWE-bench/), [Semgrep README](https://github.com/semgrep/semgrep#readme), [Scorecard non-goals](https://github.com/ossf/scorecard#project-non-goals), [Inspect scoring policy](https://inspect.aisi.org.uk/scoring-policy.html))
- Agentless's lack of a push since December 2024 makes version pinning and local review necessary if its research artifacts are reused; repository non-archive status alone is not evidence of ongoing maintenance. ([GitHub API](https://api.github.com/repos/OpenAutoCoder/Agentless))
- Semgrep offers a useful reusable OSS engine, but Rover should not make the proprietary AppSec platform, Pro Engine, or Semgrep-maintained rule licensing part of a provider-neutral trust assumption. ([licensing](https://semgrep.dev/docs/licensing))
- Scorecard's Apache-licensed scanner and its public API data are distinct from any guarantee about the scanned project; its own non-goals and check documentation make that boundary explicit. ([README](https://github.com/ossf/scorecard#readme), [check documentation](https://github.com/ossf/scorecard/blob/main/docs/checks.md))

### Gaps

- Star counts are necessarily point-in-time. The exact source and retrieval date are recorded above, but they will change.
- “Latest push” is a repository-maintenance signal, not a complete health measure. No contributor-retention, release-cadence, issue-response, dependency, or reproducible-build audit was performed for these five projects.
- No source code from the five projects was built or executed during this research, so activity, licenses, and documentation were verified from primary repositories/API objects rather than validated binaries.
- Repository license metadata does not settle third-party dataset, model, rule, or release-asset licensing. In particular, Semgrep's rules and benchmark/model datasets warrant separate review before redistribution.

## 2. How do their assurance models, artifacts, isolation, policy controls, interfaces, and costs compare?

### Takeaway

The projects cover complementary layers. SWE-bench supplies a curated issue-and-test oracle; Agentless demonstrates a bounded repair-and-rerank workflow; Inspect supplies evaluation orchestration and rich logs; Semgrep supplies policy-driven static analysis; and Scorecard supplies repository-security posture checks. None alone provides candidate acceptance, hostile-code isolation, policy integrity, and independent review. The strongest pattern is to preserve each result's scope, coverage, provenance, and failure class rather than reducing it to a green total.

### Cited Findings

#### SWE-bench

- **Evaluation/verification model:** a system receives a repository and issue and emits a patch. The harness applies the patch, runs repository tests in a Docker environment, and considers an instance resolved when the required tests pass. In the original benchmark terminology, `FAIL_TO_PASS` tests demonstrate the issue is fixed and `PASS_TO_PASS` tests check unrelated existing behavior. ([evaluation guide](https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/evaluation.md), [OpenAI benchmark explanation, 2024-08-13, updated 2025-02-24](https://openai.com/index/introducing-swe-bench-verified/))
- **Human validation:** SWE-bench Verified is a 500-instance subset selected after 93 Python-experienced software developers screened 1,699 random samples. Each sample received three independent annotations, and the most severe label determined filtering; 68.3% of sampled original instances were filtered for underspecification, unfair tests, or other major issues. ([OpenAI, published 2024-08-13, updated 2025-02-24](https://openai.com/index/introducing-swe-bench-verified/))
- **Reproducible artifacts:** predictions are JSONL containing `instance_id`, `model_name_or_path`, and `model_patch`. A run retains `results.json` and, per instance, `report.json`, `test_output.txt`, `run_instance.log`, `eval.sh`, and `patch.diff`. The current CLI can re-grade saved logs without rerunning containers. ([evaluation guide](https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/evaluation.md), [README](https://github.com/SWE-bench/SWE-bench#usage))
- **Cache integrity caveat:** the documented v5 harness caches by `run_id` and `instance_id`; rerunning the same IDs with a different patch reuses the first result. A different `run_id` is required for a changed prediction. This is a useful warning for Rover: evaluation caching must bind the candidate/patch identity, not merely a human label. ([README, “Result Caching”](https://github.com/SWE-bench/SWE-bench#usage))
- **Test isolation:** the official harness uses layered Docker images for reproducible task environments and supports parallel workers. This is benchmark-environment separation, not a documented guarantee against hostile code. ([harness reference](https://github.com/SWE-bench/SWE-bench/blob/main/docs/reference/harness.md), [Docker setup](https://www.swebench.com/SWE-bench/guides/docker_setup/))
- **Policy/security scanning:** SWE-bench does not present a general SAST, dependency-policy, secrets, or repository-governance scanner. Its assurance is test-based for the benchmarked issue. ([evaluation guide](https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/evaluation.md))
- **Integration interfaces:** Python package/CLI, JSONL predictions, Docker, Hugging Face datasets, local logs, Modal cloud evaluation, and the separate `sb-cli` submission interface are documented. ([README](https://github.com/SWE-bench/SWE-bench#readme), [evaluation guide](https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/evaluation.md))
- **Operational costs/limits:** the maintainers recommend at least 120 GB free storage, 16 GB RAM, and 8 CPU cores; ARM64 support is experimental. Published benchmark validity is also limited by public-repository contamination and narrow task/risk coverage. ([README](https://github.com/SWE-bench/SWE-bench#readme), [OpenAI limitations](https://openai.com/index/introducing-swe-bench-verified/#discussion--limitations))
- **Independent review:** Verified's multi-annotator curation improves benchmark quality, but it is curation of the benchmark, not an independent reviewer for each submitted patch. ([OpenAI methodology](https://openai.com/index/introducing-swe-bench-verified/#our-approach))

#### Agentless

- **Evaluation/verification model:** Agentless localizes likely files and edit sites, samples candidate patches, generates candidate reproduction tests, executes them against the original code, and then ranks patches using regression and reproduction results. The paper's GPT-4o experiment used 40 patch candidates and 40 reproduction-test candidates per issue. ([paper](https://arxiv.org/abs/2407.01489), [SWE-bench runbook](https://github.com/OpenAutoCoder/Agentless/blob/main/README_swebench.md))
- **Regression-test caveat:** the LLM identifies existing passing tests that should be excluded from regression selection, and the paper notes that generated reproduction tests may be incorrect; if none passes, selection falls back to regression results. This is patch ranking, not an independent acceptance oracle. ([paper, sections 3.3.1–3.3.2](https://ar5iv.labs.arxiv.org/html/2407.01489))
- **Historical results:** the paper reports 96/300 SWE-bench Lite instances resolved (32.00%), 78,166 average tokens, and $0.70 average inference cost for its GPT-4o setup. The repository's older v1.0 news reports 82/300 (27.3%) and $0.34, while later README news reports different Claude 3.5 figures. These are version-, model-, and evaluation-dependent author claims, not current independently reproduced results. ([paper](https://arxiv.org/abs/2407.01489), [README news](https://github.com/OpenAutoCoder/Agentless#news))
- **Reproducible artifacts:** the v1.5.0 release advertises complete Lite and Verified runs plus preprocessed repository structures. The runbook retains stage-specific JSONL outputs, localization/repair/test logs, regression results, reproduction results, and a final `all_preds.jsonl` prediction file. ([v1.5.0 release](https://github.com/OpenAutoCoder/Agentless/releases/tag/v1.5.0), [runbook](https://github.com/OpenAutoCoder/Agentless/blob/main/README_swebench.md))
- **Test isolation:** Agentless does not publish a separate sandbox product or threat model. Its benchmark execution path is coupled to the SWE-bench evaluation utilities, so the relevant isolation is the benchmark harness's rather than an Agentless-specific hostile-code boundary. ([paper](https://arxiv.org/abs/2407.01489), [SWE-bench harness](https://github.com/SWE-bench/SWE-bench/blob/main/docs/reference/harness.md))
- **Policy/security scanning:** there is no general source-security, dependency, secrets, or repository-policy scanner in the Agentless project. Generated tests are issue-specific validation artifacts, not a security-policy engine. ([README](https://github.com/OpenAutoCoder/Agentless#readme))
- **Integration interfaces:** the project is a collection of Python scripts/commands, consumes external model APIs, and exchanges JSONL prediction/test artifacts. It does not document a stable service API, MCP interface, or protected CI publisher. ([runbook](https://github.com/OpenAutoCoder/Agentless/blob/main/README_swebench.md))
- **Operational costs/limits:** the documented experiment requires many sampled generations and parallel test execution; the paper's historical token/cost figures do not include a current provider quote and should not be projected to 2026 models. Setup requires external API credentials and substantial per-issue execution. ([paper](https://arxiv.org/abs/2407.01489), [runbook warning](https://github.com/OpenAutoCoder/Agentless/blob/main/README_swebench.md#%EF%B8%8F-patch-validation-and-selection))

#### Inspect AI

- **Evaluation/verification model:** an Inspect task combines a dataset, solver/agent, and scorer. Scorers may be deterministic, custom Python, or model graded. Inspect distinguishes a scored verdict, a scorer error, and an unscored result; errored and unscored samples are excluded from the relevant metric denominator rather than silently counted as model success. ([official site](https://inspect.aisi.org.uk/), [scoring policy](https://inspect.aisi.org.uk/scoring-policy.html))
- **Grader independence and reproducibility:** by default a model-graded scorer can use the model under test as grader unless a separate grader model/role is bound. The framework supports a required grader role, multiple grader panels, majority reduction, temperature/seed configuration, and repeated epochs; the docs warn that provider defaults can still vary. ([model grading](https://inspect.aisi.org.uk/model-graded.html))
- **Reproducible artifacts:** each evaluation writes `.eval` or JSON logs containing status, task/model/plan metadata, results, usage statistics, samples, and reductions. `inspect log export-config` emits a run configuration that can be fed back to `inspect eval`; logs expose a schema and programmatic API. ([log files](https://inspect.aisi.org.uk/eval-logs.html))
- **Review provenance:** score edits preserve prior values and author/reason provenance; tag and metadata edits retain original values and append update history. This improves auditability but is not, by itself, cryptographic immutability or independent custody. ([log files, “Editing Logs”](https://inspect.aisi.org.uk/eval-logs.html#sec-eval-log-modification))
- **Test isolation:** built-in Docker sandboxes are per sample; generated Compose configuration defaults to `network_mode: none`, with cleanup after a task. A supplied custom Compose file **replaces** the generated configuration, so network exposure must be reviewed explicitly. Tools, agents, and scorers still run Python in the evaluation process unless their work is routed through `sandbox()`. ([sandboxing](https://inspect.aisi.org.uk/sandboxing.html))
- **Security model:** Inspect's policy says untrusted tasks, solvers, scorers, and models are equivalent to untrusted code; the `local` sandbox has no isolation, and Docker weaknesses should be reported to Docker. For genuinely untrusted code, the project recommends a stronger sandbox such as gVisor. ([SECURITY.md](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/SECURITY.md))
- **Policy/review controls:** approvers can authorize, modify, reject, escalate, or terminate tool calls before execution; reviewers can terminate or escalate after observing a result. Human and custom policies are supported. Result review is not yet implemented for bridged agents whose tools execute outside Inspect. ([tool approval](https://inspect.aisi.org.uk/approval.html), [tool result review](https://inspect.aisi.org.uk/review.html))
- **Policy/security scanning:** Inspect is not a repository SAST or dependency scanner. Its relevant controls are evaluation-time tool approval, result review, transcript/log analysis, sandbox policy, and model/scorer governance. ([official site](https://inspect.aisi.org.uk/), [approval](https://inspect.aisi.org.uk/approval.html))
- **Integration interfaces:** CLI and Python API, 20+ model providers and local inference backends, custom model/tool APIs, MCP, agent bridge, Inspect View, VS Code integration, and S3/Hugging Face/Azure log storage are documented. ([official site](https://inspect.aisi.org.uk/), [log storage](https://inspect.aisi.org.uk/eval-logs.html))
- **Operational costs/limits:** Inspect records token use and can enforce sample limits for wall time, working time, messages, turns, tokens, and configured monetary cost. Sandboxes consume CPU/memory, and agentic logs can become very large; the log documentation recommends streaming/header-only access. ([setting limits](https://inspect.aisi.org.uk/setting-limits.html), [log files](https://inspect.aisi.org.uk/eval-logs.html))

#### Semgrep

- **Evaluation/verification model:** Semgrep CE is pattern-based static analysis, not a test-execution verifier. A rule test uses annotations for expected findings (`ruleid`), expected non-findings (`ok`), and deferred cases; rule-defined fixes are tested against a separate `.fixed` fixture. Rule validation checks configuration without scanning target code. ([testing rules](https://semgrep.dev/docs/writing-rules/testing-rules))
- **Reproducible artifacts:** a reviewable rule pack should preserve YAML rules, annotated positive/negative fixtures, expected fixed-output fixtures, and the CLI/engine version. Scan output supports text, JSON, SARIF, and JUnit XML. These are reproducible *rule-test artifacts*; a finding still does not prove exploitability or absence of other defects. ([testing rules](https://semgrep.dev/docs/writing-rules/testing-rules), [CLI reference](https://semgrep.dev/docs/cli-reference))
- **Test/code-execution isolation:** ordinary CE scanning is static. The experimental `--allow-local-builds` option may execute project/dependency code and is explicitly documented as a security risk; untrusted validators are another code-execution boundary. `--autofix` modifies source and carries a data-loss warning. ([CLI reference](https://semgrep.dev/docs/cli-reference))
- **Policy/security scanning:** Semgrep can enforce custom secure-coding rules, run organization policies, perform diff-aware CI scans, apply baselines, and emit findings as blocking or nonblocking according to mode. CE's official README warns that its single-function/file analysis misses many true positives in security contexts and recommends the proprietary AppSec Platform for SAST, SCA, and secrets use cases. ([repository README](https://github.com/semgrep/semgrep#readme), [CLI reference](https://semgrep.dev/docs/cli-reference))
- **Exit-status caveat:** `semgrep scan` can exit 0 even when findings exist unless configured otherwise, while fatal/configuration/parser errors have distinct nonzero codes. Consumers must bind policy to the explicit severity/exit-code contract rather than treating any zero as “secure.” ([CLI reference](https://semgrep.dev/docs/cli-reference#exit-status))
- **Integration interfaces:** CLI (`scan`, `ci`, `test`, `validate`), JSON/SARIF/JUnit/GitLab formats, IDE/LSP and pre-commit use, CI integrations, registry rules, and a local MCP server are documented. ([CLI reference](https://semgrep.dev/docs/cli-reference), [repository README](https://github.com/semgrep/semgrep#semgrep-ecosystem))
- **Operational costs/limits:** CE can run locally and the repository says code is not uploaded by default. Remote Registry configurations send pseudonymous rule metrics by default, and metrics can be disabled. Compute, large-repository memory, rule latency, and maintenance of organization rules remain operational costs; advanced cross-file/cross-function analysis and managed products are proprietary. ([repository README, “Metrics”](https://github.com/semgrep/semgrep#metrics), [licensing](https://semgrep.dev/docs/licensing))
- **Security documentation:** the repository has a current `SECURITY.md` directing reports to `security@semgrep.com` and supporting only the latest version, but it does not publish Inspect-style sandbox scope or response-time commitments. ([SECURITY.md](https://github.com/semgrep/semgrep/blob/develop/SECURITY.md))

#### OpenSSF Scorecard

- **Evaluation/verification model:** Scorecard runs automatable repository-security heuristics. Each check returns 0–10 plus reason/details, and the aggregate is risk-weighted: critical 10, high 7.5, medium 5, low 2.5. Checks include branch protection, human code review, workflow token permissions, dangerous workflows, dependency pinning, security policy, signed releases, vulnerabilities, and maintenance. ([README, “Scoring”](https://github.com/ossf/scorecard#aggregate-score), [check documentation](https://github.com/ossf/scorecard/blob/main/docs/checks.md))
- **Policy integrity characteristics:** new checks are expected to use objective automatable data, be actionable, work without maintainer interaction, and support correction/dispute mechanisms. Each check requires low/high/inconclusive unit tests and an end-to-end test against a stable repository. ([writing a check](https://github.com/ossf/scorecard/blob/main/checks/write.md))
- **Reproducible artifacts:** the CLI emits text or JSON; `--show-details` preserves reasons and evidence. The public API result includes scan date, target repository commit, Scorecard version and commit, aggregate score, and per-check evidence/documentation. Weekly results for roughly one million critical projects are published to BigQuery. A result can therefore be interpreted only when bound to target commit and tool version. ([README](https://github.com/ossf/scorecard#readme), [public API result](https://api.scorecard.dev/projects/github.com/ossf/scorecard))
- **Release provenance:** Scorecard publishes SLSA Level 3 provenance for its own release binaries. This is provenance for the scanner release, not a signature proving the truth of a target project's score. ([README, “Verifying SLSA provenance”](https://github.com/ossf/scorecard#verifying-slsa-provenance-for-downloaded-releases))
- **Test isolation:** Scorecard is not a candidate test runner. It examines repository files, forge APIs, workflows, branch settings, release assets, and vulnerability data; there is no per-candidate execution sandbox contract because it does not claim to execute the target project's tests as acceptance evidence. ([check documentation](https://github.com/ossf/scorecard/blob/main/docs/checks.md))
- **Policy/security scanning:** Scorecard is a repository-governance and supply-chain-practice scanner, not a replacement for SAST. Its `SAST` check asks whether a project uses a recognized static-analysis tool, while its vulnerabilities check queries OSV data. ([check documentation](https://github.com/ossf/scorecard/blob/main/docs/checks.md#sast), [vulnerabilities check](https://github.com/ossf/scorecard/blob/main/docs/checks.md#vulnerabilities))
- **Security-evidence caveat:** the signed-releases check looks for signature/provenance file presence and explicitly does not verify the signature. ([signed-releases check](https://github.com/ossf/scorecard/blob/main/docs/checks.md#signed-releases))
- **Integration interfaces:** CLI, Docker image, GitHub Action, REST API, BigQuery, badges, GitLab, GitLab self-hosted, and GitHub Enterprise Server are documented. ([README](https://github.com/ossf/scorecard#using-scorecard))
- **Operational costs/limits:** unauthenticated forge requests are rate-limited; authentication and token privilege affect results. The public weekly REST scan omits CI-Tests, Contributors, and Dependency-Update-Tool due to API cost, several checks have uneven GitLab support, and the maintainers state that aggregate scores hide individual behavior and have false positives/negatives. ([README](https://github.com/ossf/scorecard#scorecard-rest-api), [project non-goals](https://github.com/ossf/scorecard#project-non-goals), [check documentation](https://github.com/ossf/scorecard/blob/main/docs/checks.md))
- **Security documentation:** Scorecard has a coordinated-disclosure policy using GitHub private vulnerability reporting, with stated acknowledgement and follow-up targets. ([SECURITY.md](https://github.com/ossf/scorecard/blob/main/SECURITY.md))

#### Cross-project assurance comparison

- **Candidate correctness:** SWE-bench and Agentless operate in this layer, but only SWE-bench's curated hidden test oracle is positioned as the benchmark's acceptance criterion. Agentless uses model-generated tests and model-assisted test selection, so its ranking evidence is weaker as an independent oracle. ([SWE-bench evaluation](https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/evaluation.md), [Agentless paper](https://arxiv.org/abs/2407.01489))
- **Evaluation governance:** Inspect has the richest explicit distinction among model verdict, evaluator malfunction, unscored result, score coverage, reviewer intervention, and retained provenance. ([scoring policy](https://inspect.aisi.org.uk/scoring-policy.html), [log files](https://inspect.aisi.org.uk/eval-logs.html))
- **Static policy enforcement:** Semgrep offers the most direct code-policy mechanism through versionable rules, fixtures, severities, and standardized outputs, but CE analysis depth and rule licensing are material limits. ([testing rules](https://semgrep.dev/docs/writing-rules/testing-rules), [licensing](https://semgrep.dev/docs/licensing))
- **Repository governance:** Scorecard is the most directly reusable model for objective, risk-tiered project-process checks, but its own documentation rejects treating the score as definitive. ([checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md), [non-goals](https://github.com/ossf/scorecard#project-non-goals))
- **Evidence reproducibility:** all four active systems retain some combination of inputs/configuration, outputs, and tool identity. SWE-bench's per-instance patch/test artifacts, Inspect's run-config export and event log, and Scorecard's target commit/tool commit/date are the most directly reusable patterns. ([SWE-bench evaluation](https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/evaluation.md), [Inspect logs](https://inspect.aisi.org.uk/eval-logs.html), [Scorecard API](https://api.scorecard.dev/projects/github.com/ossf/scorecard))

### Inferences

- A robust acceptance system needs separate states for **candidate pass**, **candidate fail**, **harness/evaluator error**, and **inconclusive/not-applicable**. Inspect's denominator policy and SWE-bench's distinction among resolved, unresolved, errored, incomplete, and infrastructure/ambiguous failures both argue against converting every non-green condition into a generic failure—or into a pass. ([Inspect scoring policy](https://inspect.aisi.org.uk/scoring-policy.html), [SWE-bench result fields](https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/evaluation.md#understanding-evaluation-results))
- Reproduction tests are most valuable as a **differential**: a credible generated test should fail for the intended reason on the base and pass on the candidate, while import/setup failures remain inconclusive. Agentless's fallback behavior illustrates why a generated test cannot become the sole authority. ([Agentless paper](https://arxiv.org/abs/2407.01489), [Rover regression semantics](../../README.md#L112-L119))
- Static findings, project-posture scores, benchmark resolution, and evaluation verdicts are orthogonal evidence. A green result in one layer cannot compensate for a red result in another unless a human-approved policy explicitly defines that tradeoff. ([Semgrep README](https://github.com/semgrep/semgrep#readme), [Scorecard non-goals](https://github.com/ossf/scorecard#project-non-goals))
- Independent review requires separation of roles. A model that generates a patch or test, an evaluator that ranks it, a policy administrator, and a signer should not all be treated as independent simply because they run in one process. ([Inspect model grading](https://inspect.aisi.org.uk/model-graded.html), [Rover security model](../../docs/SECURITY_MODEL.md#L32-L41))

### Gaps

- No project was cloned, built, or benchmarked. Docker isolation strength, rule-engine behavior, model-grader variance, API output stability, and resource use were not independently reproduced.
- No penetration test, malware fixture, policy-bypass test, or cross-project artifact-tampering test was performed.
- Published costs are historical or configuration-dependent. Agentless's figures use particular 2024 models; SWE-bench's requirements are harness resources; Inspect and Semgrep costs depend on providers and scan size; Scorecard's public service omits costly checks.
- Repository security-policy coverage is uneven. Inspect and Scorecard publish substantive threat/reporting scope, Semgrep has a minimal latest-version policy, and no root security policy was located during this review for SWE-bench or Agentless. This absence should not be converted into a claim that either project has no security process.
- The projects do not provide a common benchmark, so their percentages and scores are not directly comparable. A controlled Rover evaluation would need fixed tasks, pinned versions, frozen policies, repeated runs, and disclosed cost/resource accounting.

## 3. What can Rover learn without copying a provider-specific design?

### Takeaway

Rover should adopt portable assurance contracts—independent test curation, explicit outcome taxonomy, candidate-bound evidence, policy-rule fixtures, sandboxed execution, cost limits, and separated evaluator/reviewer authority—without adopting any benchmark leaderboard, model vendor, proprietary ruleset, cloud submission service, or organization-specific control plane. Rover's existing fail-closed parsing, counterfactual regression proof, structured outputs, review records, and constrained strategy learning are good foundations; the next step is to strengthen identity binding, independent custody, and policy administration rather than add another provider-shaped abstraction.

### Cited Findings

#### Acceptance

- Rover already treats an empty plan as inconclusive, refuses missing/malformed required results, and does not let a submitted task or provider completion claim become accepted software. It also supports Go/JUnit/SARIF/exit-code evidence and exact replay. ([Rover README](../../README.md#L43-L58), [Rover assurance overview](../../README.md#L103-L119))
- SWE-bench Verified contributes a provider-neutral lesson: acceptance criteria need human review for specification quality and fairness, conservative adjudication, retained annotations, and periodic re-curation. Its three-annotator/max-severity process is a useful model, not a requirement to copy OpenAI's dataset or governance. ([OpenAI methodology](https://openai.com/index/introducing-swe-bench-verified/#our-approach))
- Inspect contributes a cleaner outcome taxonomy: a model verdict, evaluator malfunction, and unscored/inconclusive sample are different facts. Rover should preserve that distinction through parsing, aggregation, evidence export, and human review. ([Inspect scoring policy](https://inspect.aisi.org.uk/scoring-policy.html))
- **Recommended Rover contract:** every decision should bind at least the base/source digest, candidate digest, acceptance-policy digest, complete check-plan digest, evaluator/tool version, environment identity, and result coverage. No benchmark resolve rate, Semgrep clean result, or Scorecard total should substitute for the repository's approved acceptance policy.

#### Regression testing

- Rover's existing `prove regression` requires a named intended failure on the base and a pass on the candidate, and it rejects import/setup failures as proof. That is stronger and more honest than treating any post-change green suite as a regression proof. ([Rover README](../../README.md#L112-L119))
- Agentless shows why candidate-generated reproduction tests are useful but not authoritative: tests are sampled, filtered by execution on the original repository, and may still be incorrect. Rover should treat generated tests as supplemental evidence unless they pass an approved differential and policy. ([Agentless paper](https://arxiv.org/abs/2407.01489))
- Semgrep provides a strong meta-testing pattern for Rover's own assurance components: every rule/policy should have a positive fixture, negative fixture, and expected-fix fixture. Rover can apply this to SARIF/JUnit interpretation, required-result logic, test-change heuristics, mutation interpretation, policy exceptions, and evidence parsers. ([Semgrep rule testing](https://semgrep.dev/docs/writing-rules/testing-rules))
- Scorecard's check-development contract—objective data, actionable remediation, low/high/inconclusive unit cases, and stable end-to-end fixtures—maps well to Rover acceptance checks. ([Scorecard check authoring](https://github.com/ossf/scorecard/blob/main/checks/write.md))
- **Recommended Rover contract:** retain the full required-check set; use counterfactual tests for intended behavior; add rule/policy regression fixtures; run a full baseline periodically; and use diff-aware security scans only as an optimization when their policy and omitted history are explicit. Semgrep's baseline mode illustrates diff-aware reporting, but Rover must not confuse “new findings only” with a full clean scan. ([Semgrep CLI](https://semgrep.dev/docs/cli-reference))

#### Evidence and reproducibility

- SWE-bench retains the exact patch, test command, test output, per-instance report, and execution log. Inspect retains a reproducible run configuration, sample outputs/events, usage, and score-edit provenance. Scorecard's API binds results to date, target commit, tool version/commit, and check-level evidence. These are portable evidence dimensions, not provider-specific UI features. ([SWE-bench artifacts](https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/evaluation.md#understanding-evaluation-results), [Inspect logs](https://inspect.aisi.org.uk/eval-logs.html), [Scorecard API](https://api.scorecard.dev/projects/github.com/ossf/scorecard))
- **Recommended Rover evidence envelope:** retain immutable raw stdout/stderr and structured reports; exact command/argv and environment policy; base and candidate content hashes; check and acceptance-policy digests; tool/parser versions; container/image digest where applicable; start/end time and resource usage; pass/fail/error/inconclusive/not-applicable status; expected-versus-observed test identities; reviewer identity, timestamp, and reason; and links to every retained artifact.
- Cache keys should include the candidate and full evaluation contract. SWE-bench explicitly warns that a `run_id`/`instance_id` cache can reuse a result after the patch changes. ([SWE-bench README](https://github.com/SWE-bench/SWE-bench#usage))
- Evidence should distinguish raw observation from interpretation: raw test output is evidence; a parser verdict is derived evidence; an agent's explanation is a claim. Rover's security model already makes this distinction. ([Rover security model](../../docs/SECURITY_MODEL.md#L32-L41))
- Signing should be described narrowly. Rover's current signatures prove signature validity relative to a supplied key, not correctness, independent administration, SLSA level, or universal acceptance. Scorecard's SLSA release provenance similarly authenticates its scanner release, not the correctness of a scan finding. ([Rover README](../../README.md#L155-L157), [Scorecard release provenance](https://github.com/ossf/scorecard#verifying-slsa-provenance-for-downloaded-releases))

#### Policy integrity

- Semgrep demonstrates that policy should be explicit, versionable data with stable rule IDs, severities, messages, positive/negative fixtures, and machine-readable outputs. Rover already parses SARIF and protects required-check integrity, but it can strengthen this into a first-class policy-bundle lifecycle. ([Semgrep rule testing](https://semgrep.dev/docs/writing-rules/testing-rules), [Rover README](../../README.md#L112-L119))
- Scorecard demonstrates the value of actionable, per-check reasons and remediation, while warning against aggregate-score opacity. Rover should preserve every check result and reason even when presenting a concise decision. ([Scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md), [non-goals](https://github.com/ossf/scorecard#project-non-goals))
- Rover's learning mechanism currently may reorder only the complete approved check list and cannot remove checks; that is an important policy-integrity boundary to preserve. ([Rover README](../../README.md#L159-L163))
- **Recommended Rover contract:** version acceptance/security policy as a reviewed bundle; bind every run to its digest; validate policy syntax and fixture behavior before activation; require a separate administrator or protected CI authority for activation; record scoped exceptions with owner, reason, compensating control, and expiry; and prevent candidates, agents, and learning optimizers from weakening or silently reinterpreting required policy.
- Suppression mechanisms need the same treatment as code: a `nosem`, ignored test, baseline, score threshold, or exception should be an auditable policy event rather than invisible absence. Semgrep documents `nosem`, baseline commits, and `--error`; Scorecard supports maintainer annotations/disputes; Rover can apply the same explicitness without adopting either product's policy syntax. ([Semgrep CLI](https://semgrep.dev/docs/cli-reference), [Scorecard check requirements](https://github.com/ossf/scorecard/blob/main/checks/write.md))

#### Independent review

- Inspect separates tool approval before execution from result review after execution, supports human escalation, and records review events. It also makes the independence limitation visible: bridged-agent tool results are not yet reviewable, and an approval can mean “permitted,” not “executed.” ([tool approval](https://inspect.aisi.org.uk/approval.html), [tool result review](https://inspect.aisi.org.uk/review.html))
- Inspect's model grader can be explicitly separated from the model under test, and multiple graders can vote. The portable lesson is to require a declared evaluator role and record its identity/configuration—not to require any particular model vendor. ([model grading](https://inspect.aisi.org.uk/model-graded.html))
- SWE-bench Verified's three-human curation process is a useful acceptance-criteria review model, but it does not review every submitted patch. ([OpenAI methodology](https://openai.com/index/introducing-swe-bench-verified/#our-approach))
- **Recommended Rover contract:** separate at least producer, evaluator, policy administrator, reviewer, and signer; bind identities and decisions in evidence; prefer deterministic or human-reviewed criteria where feasible; use model grading only as a declared, versioned evaluator; retain disagreements and abstentions; and require a protected reviewer/evaluator with no candidate-write authority for high-impact acceptance.
- Rover's current local owner controls the signer, store, code, tests, labels, and policy, so local review and signing are not independent. A future independent-review path should use separate credentials, protected CI or a remote verifier, append-only/transparency-friendly publication, and narrowly scoped signing authority. ([Rover security model](../../docs/SECURITY_MODEL.md#L39-L54), [Rover unsupported guarantees](../../docs/SECURITY_MODEL.md#L56-L60))

#### Isolation, resources, and interfaces

- Inspect provides a useful provider-neutral isolation contract: one disposable sandbox per sample, no network by default, explicit opt-in for networking, per-container resource limits, cleanup, and an extension API for stronger backends. It also candidly states that custom tasks and non-sandboxed Python remain trusted code. ([Inspect sandboxing](https://inspect.aisi.org.uk/sandboxing.html), [Inspect security policy](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/SECURITY.md))
- SWE-bench demonstrates the reproducibility value of immutable environment images, but its benchmark harness should not be treated as a general hostile-code sandbox. ([SWE-bench harness](https://github.com/SWE-bench/SWE-bench/blob/main/docs/reference/harness.md))
- Semgrep shows a useful default-deny distinction: static scanning normally does not execute project code, while experimental project builds and remote validators are explicit security-risk switches. ([Semgrep CLI](https://semgrep.dev/docs/cli-reference))
- **Recommended Rover contract:** make execution profiles explicit—read-only/static, restricted test execution, networked integration, and privileged/administrative operations—with ephemeral workspaces, scrubbed environments, resource/output/time limits, default-deny network, and no silent fallback. A restricted profile should not be advertised as hostile-code isolation until an appropriate backend and independent tests support that claim.
- Inspect's time, working-time, message, turn, token, and cost limits map to Rover's need for task-, workflow-, attempt-, provider-, and retry-bound budgets. Limits should be charged before or at resource admission and survive retries, not reset merely because a new task key or provider session is used. ([Inspect limits](https://inspect.aisi.org.uk/setting-limits.html), [Rover status](../../STATUS.md#L12-L18))
- **Recommended Rover integration boundary:** keep a small canonical, versioned result schema and adapters for exit code, JUnit, SARIF, SWE-bench-style per-instance reports, and Inspect-like evaluation logs. Keep optional imports/exports local or explicitly authorized. Rover's MCP/API surface should continue to deny approval, signing, grant creation, merge, and deployment tools by default. ([Rover security model](../../docs/SECURITY_MODEL.md#L15-L30))

#### A provider-neutral priority order

1. **Evidence identity first:** bind decisions and caches to base, candidate, policy, check plan, parser/tool version, and environment; retain raw plus structured artifacts and explicit coverage/error states. This follows the strongest shared evidence pattern across SWE-bench, Inspect, and Scorecard. ([SWE-bench artifacts](https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/evaluation.md#understanding-evaluation-results), [Inspect logs](https://inspect.aisi.org.uk/eval-logs.html), [Scorecard API](https://api.scorecard.dev/projects/github.com/ossf/scorecard))
2. **Policy and parser regression second:** add positive, negative, malformed, and expected-fix fixtures for Rover's own gates and policy rules. ([Semgrep testing](https://semgrep.dev/docs/writing-rules/testing-rules), [Scorecard check authoring](https://github.com/ossf/scorecard/blob/main/checks/write.md))
3. **Independent evaluator and protected review third:** separate candidate production, evaluation, policy activation, review, and signing authority. ([Inspect model grading](https://inspect.aisi.org.uk/model-graded.html), [Rover security model](../../docs/SECURITY_MODEL.md#L39-L54))
4. **Stronger isolation and cost admission fourth:** add reviewed, provider-neutral execution profiles and budgets before expanding autonomous repair or remote execution. ([Inspect sandboxing](https://inspect.aisi.org.uk/sandboxing.html), [Inspect limits](https://inspect.aisi.org.uk/setting-limits.html))
5. **Optional adapters last:** add benchmark, SAST, or evaluation-log interoperability only after Rover's canonical evidence and policy contracts are stable, so integrations remain replaceable and do not dictate the core model.

### Inferences

- The common architecture is not “benchmark + agent + security score.” It is **candidate identity → fixed acceptance contract → isolated observations → typed outcomes → retained provenance → human or policy-governed decision**. Each source project covers only part of that chain. ([SWE-bench evaluation](https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/evaluation.md), [Inspect scoring policy](https://inspect.aisi.org.uk/scoring-policy.html), [Semgrep testing](https://semgrep.dev/docs/writing-rules/testing-rules), [Scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md))
- Rover's terminal-first, agent-neutral posture is an architectural advantage if adapters remain outside the core acceptance model. Rover should import evidence and policy formats, not make its state model mirror OpenAI, Modal, Semgrep AppSec, UK AISI, or OpenSSF deployments. ([Rover README](../../README.md#L32-L58), [Rover tool interfaces](../../README.md#L121-L143))
- Independent review cannot be achieved by adding another local command or signature key. It requires a distinct authority boundary, protected storage/publication, and a review decision that the candidate cannot rewrite. ([Rover security model](../../docs/SECURITY_MODEL.md#L39-L54))
- A benchmark or scanner should be advisory evidence unless a repository's reviewed policy explicitly promotes a particular condition to a hard gate. This preserves composability without making external projects' scores part of Rover's trust model. ([Scorecard non-goals](https://github.com/ossf/scorecard#project-non-goals), [Rover learning boundary](../../README.md#L159-L163))

### Gaps

- These are design implications, not implemented Rover features or validated conclusions. No Rover code, schema, interface, or test was changed by this research.
- The proposed canonical evidence envelope and policy-bundle lifecycle require explicit schemas, compatibility/migration rules, threat modeling, and regression tests before implementation.
- A fair comparison would require running pinned versions of these projects on owned fixtures and measuring detection, false-positive/false-negative behavior, reproducibility, isolation, latency, and resource cost. This desk review does not supply those measurements.
- Independent reviewers have not validated the recommendations, and no hosted CI, external verifier, transparency log, or protected signer was tested.
- Vendor and benchmark claims were deliberately not copied into Rover's evidence. Any future integration must preserve source identity, tool version, rule/policy digest, limitations, and the distinction between observed output and third-party assertion.
